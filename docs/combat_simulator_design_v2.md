# Apex 3v3 战斗模拟器系统设计 v2

## 一、系统概述

本系统用于模拟《Apex 英雄》风格的 3v3 团队战斗。用户可分别配置两支队伍在 **枪法**、**战斗经验**、**地形优势** 三个维度上的属性值。点击开始后，系统基于按 tick 执行的时间机制实时模拟战斗过程，逐阶段输出战斗日志，直至一方全灭或达到其他胜负条件。

本系统的核心设计采用 **Burst-Fire 交火模型**，模拟真实 Apex 战斗中的 TTK 节奏：队员连续射击一组子弹，逐发判定命中，先破甲再打人，弹匣打空后换弹，破甲后缩回掩体打电池，被集火时被迫缩掩体，队友倒地后需要救援。整个战斗过程由状态机驱动，配合抽象掩体系统和属性加权公式，输出贴近真实战斗的详细战况。

---

## 二、核心设计：Burst-Fire 交火模型

### 2.1 基本战斗节奏

每个队员的战斗行为遵循以下节奏：

1. **进入射击状态**后，连续射出一组子弹（burst，5~8 发）。
2. **每 2 ticks 结算一发**，逐发判定命中与伤害。
3. **弹匣容量 20 发**，打空后强制进入换弹状态（18 ticks），期间完全无法攻击。
4. **先打护盾**，护盾归零触发"破甲"事件。
5. **破甲后**队员会尝试退回掩体打电池（15 ticks），恢复护盾后再探头继续战斗。

所有人统一伤害模型，差异仅来自队伍三属性和当前战斗状态。

### 2.2 弹匣与弹药管理

- 每个队员拥有弹匣容量：20 发。
- 射击时以 burst 为单位消耗弹药。
- 弹匣剩余 ≤ 3 发且场上存在可攻击目标时，优先把剩余弹药打光，然后强制换弹。
- 换弹期间完全无法攻击，也无法执行其他动作。

## 三、数据结构设计

### 3.1 队伍属性（全局参数）

| 属性 | 含义 | 影响范围 |
|------|------|----------|
| 枪法 | 射击精准度与暴击率 | 命中率、爆头概率 |
| 战斗经验 | 战场应变与生存能力 | 被命中概率折扣、倒地流血倒计时长度 |
| 地形优势 | 对地图环境的利用 | 掩体质量、先手压制权 |

每个属性的实际效果映射为内部系数，例如枪法系数 = 属性值 / 50，范围 0~2。

### 3.2 队员实例属性（动态）

| 字段 | 类型 | 初始值 | 说明 |
|------|------|--------|------|
| `id` | string | - | 唯一标识 |
| `teamId` | string | - | 所属队伍 |
| `hp` | number | 100 | 生命值，上限 100 |
| `isDown` | boolean | false | 是否倒地 |
| `shield` | number | 50 | 护盾值，上限 50 |
| `magAmmo` | number | 20 | 当前弹匣剩余弹药 |
| `state` | string | `'idle'` | 当前状态 |
| `stateTimer` | number | 0 | 当前状态剩余 ticks |
| `downTimer` | number | 0 | 倒地流血倒计时（ticks） |
| `isDead` | boolean | false | 是否已淘汰（死亡），死亡后不再参与任何战斗行为 |

**状态枚举**：`idle` / `shooting` / `reloading` / `healing_shield` / `healing_hp` / `reviving` / `in_cover` / `dead`

### 3.3 状态机属性对照表

| 状态 | 能否被击中 | 命中率修正 | 能否主动行动 | 说明 |
|------|-----------|-----------|-------------|------|
| `idle` | ✅ 正常 | ×1.0 | ✅ | 空闲，等待决策 |
| `shooting` | ✅ 正常 | ×1.0 | ✅（射击中） | 开火，逐发结算 |
| `reloading` | ✅ 正常 | ×1.0 | ❌ | 换弹，18 ticks |
| `healing_shield` | ✅ 正常 | ×0.35 | ❌ | 打电池，15 ticks |
| `healing_hp` | ✅ 正常 | ×0.35 | ❌ | 打医疗包，12 ticks |
| `reviving` | 拉人者❌ 被拉者✅ | 拉人者×0.35 | ❌ | 救援，20 ticks |
| `in_cover` | ✅ | ×0.35 | ❌ | 被压制缩回掩体，5 ticks |
| `dead` | ❌ | - | ❌ | 已淘汰，不再参与战斗，无法被选中为目标 |

## 四、状态机与流转设计

### 4.1 每 tick 执行顺序

```
1. 【状态倒计时递减】stateTimer -= 1
   → 若 stateTimer > 0：保持当前状态，执行该状态效果，跳过后续决策
   → 若 stateTimer == 0：状态结束，进入"状态退出判定"

2. 【状态退出 → 选择下一状态】
   ┌─────────────────────────────────────────────────────────────┐
   │ 上一状态          │ 退出后 → 下一状态                       │
   ├─────────────────────────────────────────────────────────────┤
   │ shooting          │ 弹匣空 → reloading；被打缩了 → in_cover │
   │ reloading         │ → idle（装填完毕）                       │
   │ healing_shield    │ → idle（护盾回满至 50）                  │
   │ healing_hp        │ → idle（HP 回满或上限）                  │
   │ reviving          │ → idle（成功/被打断）                    │
   │ in_cover          │ → idle（压制结束）                       │
   └─────────────────────────────────────────────────────────────┘

3. 【idle 状态下的主动决策】（仅 idle 状态进入此步骤）

   准入检查：若队员 `isDead == true`、`isDown == true` 或 `hp <= 0`，直接跳过决策，保持 idle。

   按以下优先级逐一检查，满足即进入对应状态：

   a) 弹匣剩余 ≤ 3 发，且场上存在可攻击目标
      → 强行打完剩余弹药 → reloading (18 ticks)

   b) shield == 0，且身边无队友正在拉你，且未在被集火
      → healing_shield (15 ticks)

   c) HP ≤ 25，且未被集火
      → healing_hp (12 ticks)

   d) 有队友处于倒地状态，且自己不是唯一站着的队员，且未在被集火
      → reviving (20 ticks)

   e) 场上存在可攻击目标
      → shooting：
         · burst 长度 = random(5, 8)
         · 每 2 ticks 结算一发
         · stateTimer = burst长度 × 2

   f) 以上均不满足
      → 保持 idle
```

### 4.2 关键强制流转

#### 被打缩了（Suppression）
- 本 tick 内，若一名队员**被命中 ≥ 2 发**，下一 tick 强制进入 `in_cover` (5 ticks)。
- `in_cover` 期间不攻击、不治疗、不拉人。
- 模拟 Apex 中被一梭子锁到时不敢探头的感觉。

#### 救援打断
- `reviving` 状态的队员若本 tick 被命中，立即退出 `reviving` → `idle`。
- 被救队友保持倒地状态不变。
- 若被救队友期间被补掉（HP 归零），救援直接失败。

#### 破甲事件
- 护盾从 >0 降至 0 的瞬间，触发**破甲**日志事件。
- 破甲不影响当前状态，但会提高该队员在下一次 idle 时进入 `healing_shield` 的优先级。

## 五、掩体设计

### 5.1 设计原则

掩体不是坐标系中的物理对象，而是**每个队员当前状态的抽象属性**。

在一个战斗实例（combat）内，掩体系统只回答一个问题：**"打这个人的命中率要打折吗？"**

### 5.2 掩体系数表

| 掩体等级 | 系数 | 触发条件 |
|---------|------|---------|
| 无掩体 | ×1.0 | idle、shooting 状态 |
| 普通掩体 | ×0.6 | shooting 状态（默认视为探头射击） |
| 优秀掩体 | ×0.35 | healing_shield、healing_hp、reviving（拉人者）、in_cover |

### 5.3 地形优势的影响

地形优势属性直接决定双方掩体质量：

```
地形优势差 = 攻方队伍地形属性 - 守方队伍地形属性
```

| 差值范围 | 效果 |
|---------|------|
| > 20 | 攻方命中率额外 +15%；守方掩体失效，强制按"无掩体"计算 |
| -20 ~ 20 | 正常计算，按状态取对应掩体系数 |
| < -20 | 攻方命中率额外 -15%；守方掩体升级为"优秀掩体"（取 0.35） |

这样地形优势直接决定了谁能先破甲、谁会被按在掩体后不敢露头。

## 六、命中与伤害公式

### 6.1 单发命中率

```
基础命中率 = 0.6
枪法系数 = 攻方枪法属性 / 50
经验系数 = 1 + 0.005 × 守方战斗经验属性
地形修正 = 根据地形优势差计算（见 5.3）
掩体修正 = 根据守方当前状态取掩体系数（见 5.2）

实际命中率 = 基础命中率 × 枪法系数 / 经验系数 × 地形修正 × 掩体修正

最终命中率 clamp 至 [0.05, 0.95]
```

### 6.2 伤害计算

```
单发基础伤害 = 15

爆头判定：
  爆头概率 = 0.1 × 枪法系数
  若触发爆头 → 伤害 × 1.75

实际伤害 = 单发基础伤害（×1.75 若爆头）
```

所有人统一伤害。枪法只影响"能不能打中"和"能不能爆头"，不影响单发伤害。

### 6.3 受击结算顺序

1. 若 `shield > 0`：
   - `shield -= 实际伤害`
   - 若 `shield <= 0`：触发**破甲**事件，溢出伤害不传导至 HP
2. 若 `shield == 0`：
   - `hp -= 实际伤害`
   - 若 `hp <= 0`：进入**倒地**状态

### 6.4 目标选择 AI

目标选择遵循以下优先级：

1. **已破甲且无护盾的敌方**（最脆弱，容易秒掉）。
2. **正在 reloading / healing_shield / healing_hp 的敌方**（无法反击，安全输出窗口）。
3. **当前 HP 最低的敌方**。
4. **正在被队友攻击的敌方**（集火逻辑，提升 20% 优先级权重）。
5. 随机扰动（防止过于呆板，±10% 浮动）。

## 七、倒地与救援系统

### 7.1 倒地触发

- HP 降至 ≤ 0 时，状态变为 `isDown = true`。
- 倒地瞬间不淘汰，进入**流血倒计时**。

### 7.2 流血倒计时

```
基础倒地倒计时 = 100 ticks
经验加成 = 守方战斗经验属性 × 0.5

实际倒计时 = 基础倒计时 + 经验加成
```

- 经验高的队员倒地后存活更久，给队友更多救援时间。
- 倒计时归零且未获救 → 淘汰（`isDead = true`，`hp = 0`）。

### 7.3 救援机制

- 队友处于 `idle` 状态（或 shooting 结束后），可进入 `reviving` (20 ticks)。
- 救援期间拉人者无法攻击，被拉者保持倒地。
- **可打断**：拉人者若被命中，立即退出 `reviving`，救援失败。
- **救援成功**：被救队员 HP = 25，`isDown = false`，`shield = 0`（无护盾，需自己打电池）。

### 7.4 补人逻辑

- 敌方有队员倒地时，攻击方有 **70% 概率**选择"补掉"（继续攻击倒地者）。
- 补掉判定：倒地者被命中时直接扣 HP，HP ≤ 0 立即淘汰（`isDead = true`，`hp = 0`，无视倒地倒计时）。
- 若选择不补，则攻击站着的敌人。

## 八、战斗模拟流程（按 tick 执行）

### 步骤 1 - 战斗实例初始化

当两个队伍在地图相遇进入 `fight` 状态时：

1. 从队伍属性计算枪法系数、经验系数。
2. 初始化每个队员：`hp = 100`，`shield = 50`，`magAmmo = 20`，`state = 'idle'`，`stateTimer = 0`。
3. 计算两队地形优势差，记录为 combat 的上下文参数。

### 步骤 2 - 主循环（每个 tick）

#### 2.1 Tick 更新
- `tick += 1`
- 所有队员 `stateTimer` 递减。
- 倒地队员 `downTimer` 递减，归零 → 淘汰。

#### 2.2 状态结算（按队员顺序）
- 对每名队员，根据当前 `state` 执行对应效果：
  - `shooting`：若本 tick 是"发弹 tick"（每 2 ticks 一次），执行命中判定与伤害结算。
  - `reloading` / `healing_shield` / `healing_hp` / `reviving` / `in_cover`：仅倒计时，无其他效果。
  - `idle`：进入主动决策流程（见 4.1 步骤 3）。

#### 2.3 命中判定与伤害结算
- 对 shooting 状态的队员，逐发判定：
  - 根据目标选择 AI 选取目标。
  - 计算命中率（综合枪法、经验、地形、掩体）。
  - 随机数判定命中 → 计算伤害 → 扣护盾/HP → 检查破甲/倒地/淘汰。
  - 记录命中次数，用于下一 tick 的"被打缩了"判定。

#### 2.4 强制状态流转
- 扫描所有队员本 tick 被命中次数：
  - ≥ 2 发 → 下一 tick 强制进入 `in_cover`。
- 扫描 `reviving` 队员：
  - 若本 tick 被命中 → 立即中断救援。

#### 2.5 胜负判定
- 若某队已无站立队员（全员 `isDown` 或已淘汰）→ 对方胜利，战斗立刻结束。
- 若 combat 内仅剩一队存活 → 战斗结束，存活队继续跑图/搜刮。

#### 2.6 输出实时日志
- 每个关键事件即时推送到输出队列：
  - 命中/破甲/倒地/救援成功/淘汰/换弹/打电池完成
- 日志格式示例见第九章。

## 九、即时输出机制

### 9.1 事件类型与示例

系统使用**事件流**模式：模拟引擎在产生事件的 tick 时，立即推送到输出队列。前端轮询或 WebSocket 接收事件并动态追加到显示区域。

| 事件 | 日志示例 |
|------|---------|
| 命中 | `[Tick 45] TeamA-恶灵 命中 TeamB-直布罗陀，护盾-15 (剩余 35)` |
| 破甲 | `[Tick 48] 💥 TeamB-直布罗陀 护盾破碎！` |
| 打电池 | `[Tick 49] TeamB-直布罗陀 缩回掩体打电池...` |
| 电池完成 | `[Tick 64] TeamB-直布罗陀 护盾恢复完毕！` |
| 爆头 | `[Tick 52] TeamA-猎犬 爆头 TeamB-恶灵！伤害 26！` |
| 倒地 | `[Tick 55] TeamB-恶灵 被击倒！剩余 2 人站立。` |
| 换弹 | `[Tick 56] TeamA-恶灵 弹匣打空，换弹中...` |
| 救援 | `[Tick 60] TeamB-直布罗陀 开始救援 恶灵...` |
| 救援成功 | `[Tick 80] ✅ TeamB-恶灵 被救起！(25 HP，无护盾)` |
| 救援打断 | `[Tick 65] ❌ TeamB-直布罗陀 救援被打断！` |
| 补人 | `[Tick 58] TeamA-猎犬 补掉了 TeamB-恶灵！` |
| 淘汰 | `[Tick 90] 💀 TeamB-命脉 流血过久，已被淘汰。` |
| 被压制 | `[Tick 62] TeamA-恶灵 被火力压制，缩回掩体！` |

### 9.2 速度控制

前端通过调整每 tick 的实际等待时间来控制播放速度（如 ×1、×2、×5）。引擎内部只负责按 tick 生成事件，不感知播放速度。

## 十、与大逃杀框架的对接

本战斗模拟器是大逃杀赛事系统的一个子模块，负责处理两队相遇后的微观战斗过程。外围框架（缩圈、移动、劝架、赛事积分、前端渲染）通过标准接口调用本模块。

### 10.1 接口约定

战斗引擎暴露如下接口：

```javascript
function processCombatTick(combat, teams, tick, globalState)
```

- **输入**：当前 combat 实例、交战各队的队员数据、当前 tick、全局状态。
- **输出**：更新后的队员状态（HP、shield、isDown、state 等）、战斗事件日志、胜负结果。

### 10.2 数据格式

引擎内部维护队员的扩展字段（shield、magAmmo、state、stateTimer、downTimer）。战斗结束后，输出标准格式的队员状态（hp、isDown），供外围框架继续处理（跑图、搜刮、积分结算等）。

### 10.3 职责边界

| 模块 | 职责 |
|------|------|
| 大逃杀框架 | 缩圈、队伍移动、战斗触发、劝架、赛事积分、前端地图渲染 |
| 战斗引擎 | 两队相遇后的微观交火、状态机驱动、命中伤害结算、胜负判定 |

## 十二、总结

本系统通过以下机制模拟贴近真实的 Apex 3v3 战斗：

- **Burst-Fire 连射**：射击有连贯性（一梭子 5~8 发，逐发判定），弹匣打空后强制换弹。
- **护盾与破甲**：受击先扣护盾，破甲后队员会缩回掩体打电池，创造真实的 TTK 层次。
- **状态机驱动**：队员自动完成换弹、打电池、拉人、缩掩体等行为，无需手动干预。
- **抽象掩体**：当前状态决定掩体质量，地形优势差直接影响命中率。
- **集火与补人**：AI 会优先攻击脆弱目标，倒地后可被补掉。
- **压制与救援**：被集火时会强制缩掩体，救援可被打断。

整个系统基于 tick 驱动，通过标准接口与大逃杀赛事框架对接，输出详细的战斗事件流供前端实时展示。
